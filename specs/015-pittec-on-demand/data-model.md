# Data Model: PitTec sob demanda

## Conventions

- UUIDs are generated server-side unless supplied as an idempotency key.
- All timestamps are `timestamptz` in UTC; UI formatting uses the device locale.
- Exact latitude/longitude use PostGIS `geography(Point, 4326)` or the existing
  equivalent columns. Contract coordinates are always WGS84.
- Existing tables remain authoritative. This document describes additive
  changes in a new forward-only migration.
- `auth.uid()` and RLS identify the caller; client-supplied role/provider IDs are
  never trusted.

## Relationship overview

```text
auth.users
  ├── providers ── provider_services ── services ── service_categories
  │       └── provider_discovery_locations
  └── service_searches ── dispatch_candidates
               └── appointments
                      ├── provider_current_locations
                      ├── client_current_locations
                      └── appointment_route_snapshots
```

## Existing entities changed

### `services`

Purpose: catalog entry and dispatch behavior.

| Field | Change | Rules |
|---|---|---|
| `dispatch_kind` | extend allowed values | Add `PITTEC_AUTO_SEQUENTIAL`; preserve `BROWSE` and `MOBILE_SEQUENTIAL`. |

Seed one active category/service named `PitTec` with dispatch kind
`PITTEC_AUTO_SEQUENTIAL` and copy that explicitly explains “Tec” as “Técnico”.
The seed is idempotent and preflights conflicting records. The home catalog RPC
includes this active card even when no provider offer exists; `min_price` may be
null. Existing catalog behavior is unchanged for other services.

### `providers`

Purpose: provider profile and effective working mode.

| Field | Change | Rules |
|---|---|---|
| `location_mode` | extend allowed values | `FIXED`, `MOBILE`, `PITTEC`. |
| `pending_location_mode` | new nullable text | Same allowed values; differs from effective mode only while an appointment is active. |

Invariants:

- `PITTEC` does not change the account role: the account remains `PROVIDER`.
- If no non-terminal appointment exists, changing mode updates
  `location_mode` immediately and clears `pending_location_mode`.
- During an active appointment, changing mode writes only
  `pending_location_mode`.
- The RPC that performs the terminal transition applies the pending value and
  clears it atomically.
- Availability for PITTEC requires notification permission/channel readiness;
  that client-side prerequisite supplements, but does not replace, backend
  eligibility.

### `provider_services`

Purpose: active service offers. No schema change is required.

PitTec eligibility requires an active offer for the PitTec service and the
existing valid price/duration fields. Price stays internal to current business
rules and is not shown in the new PitTec request UI.

### `provider_discovery_locations`

Purpose: one recent discovery location per available mobile provider. No schema
change is required unless the current revision column is absent.

Invariants for PitTec:

- Accept updates only from the authenticated provider with effective
  `location_mode = PITTEC`, availability enabled and acceptable accuracy.
- A point older than the existing freshness threshold is ineligible.
- Exact rows are never directly selectable by clients.
- During `ACCEPTED`/`IN_PROGRESS`, a PitTec publishes exact movement only to
  `provider_current_locations`; its discovery point is removed or excluded.
- Terminal transitions may resume discovery only if the provider remains
  available with effective mode PITTEC.

The public/client projection is generated by `list_nearby_pittecs`, using a
stable server-side grid of approximately 500 m and an opaque marker identifier.

### `service_searches`

Purpose: durable client request and sequential-dispatch state.

Existing fields and states are reused. For PitTec, the search also records:

| Field | Requirement |
|---|---|
| request coordinate | exact WGS84 point, server-private |
| accuracy | finite, positive and within accepted limit |
| `captured_at` | required and recent enough at request start |
| revision | increments on every visible transition |
| current candidate/appointment | exactly one while awaiting a provider |

PitTec state interpretation:

| State | Meaning | Allowed next states |
|---|---|---|
| `SEARCHING` | transaction is choosing next eligible provider | `AWAITING_PROVIDER`, `NO_PROVIDER`, `CANCELLED` |
| `AWAITING_PROVIDER` | one `PENDING` offer exists until `offer_expires_at` | `SEARCHING`, `ACCEPTED`, `CANCELLED`, `NO_PROVIDER` |
| `ACCEPTED` | provider is on the way | `IN_PROGRESS`, `CANCELLED` |
| `IN_PROGRESS` | provider confirmed arrival | `COMPLETED`, `CANCELLED` |
| terminal state | request ended | none |

PitTec invariant: at most one non-terminal `PITTEC_AUTO_SEQUENTIAL` search exists
per client. Legacy dispatch kinds retain their existing simultaneity rules. The
migration preflight must report conflicting active PitTec rows before adding the
partial unique enforcement.

Exact request coordinates are cleared or made inaccessible after a terminal
transition according to the existing retention policy.

### `dispatch_candidates`

Purpose: ordered audit of providers evaluated for one search.

For PitTec:

- Candidate distance is calculated against exact server-side coordinates.
- Ordering is `distance ASC`, then stable UUID tie-breaker.
- Radii are evaluated in order: 10 km, 25 km, 50 km.
- A provider is inserted at most once per search; a unique `(search_id,
  provider_id)` constraint or equivalent conflict-free insert enforces this.
- Selection sets `PRESENTED` and immediately `REQUESTED` in the same transaction
  because the client does not manually choose a candidate.
- `REJECTED`, `EXPIRED`, `CANCELLED_BY_PROVIDER`, `ACCEPTED` are terminal for a
  candidate. None becomes eligible again within that search.

The existing cycling behavior remains available only to the legacy dispatch
kind.

### `appointments`

Purpose: provider offer and accepted service appointment.

| Field | Change | Rules |
|---|---|---|
| `arrived_at` | new nullable timestamp | Set once by the PitTec “Cheguei” RPC; immutable afterward. |
| `offer_expires_at` | existing/required for PitTec | Exactly 60 s after the offer is issued. |
| revision/version | existing | Required for optimistic concurrency and notification deduplication. |

PitTec transitions:

```text
PENDING --accept--> ACCEPTED --arrive--> IN_PROGRESS --complete--> COMPLETED
   │                    │                     │
   ├--reject/timeout----┴--provider cancel----┴--> search next or NO_PROVIDER
   └--client cancel------------------------------> CANCELLED
```

Rules:

- Accept succeeds only for the assigned provider before expiration.
- A late or duplicated response returns the current authoritative snapshot and
  does not modify another offer.
- “Cheguei” is provider-only and requires `ACCEPTED`.
- PitTec completion is provider-only and requires `IN_PROGRESS`.
- After acceptance, either participant can cancel and must provide a nonblank
  reason. Provider cancellation returns the client search to server-side
  selection; client cancellation ends it.
- When no untried provider remains inside 50 km, state becomes `NO_PROVIDER`.
- Terminal processing clears private live data and applies a pending modality.

### `provider_current_locations`

Purpose: exact current position of the assigned provider during an accepted
appointment.

RLS permits read only to the provider and client belonging to the appointment;
write is restricted to the assigned provider. Updates require active
`ACCEPTED`/`IN_PROGRESS`, finite coordinates, acceptable accuracy, monotonic
`captured_at` and server-side revision increment.

### `client_current_locations`

Purpose: exact service destination during an accepted appointment.

On acceptance, the dispatch transaction copies the private request point here
so the provider can calculate a route immediately, even before the client opens
the tracking screen. Later client updates follow the existing monotonic and RLS
rules. Only participants can read the row.

## New entity

### `appointment_route_snapshots`

Purpose: hold one current normalized route shared by both participants, without
creating travel history.

| Field | Type | Constraints |
|---|---|---|
| `appointment_id` | uuid | primary key; FK to `appointments` with cascade delete |
| `provider_location_revision` | bigint | positive; identifies input position |
| `geometry` | jsonb | GeoJSON LineString coordinates in `[lon, lat]`; validated size/range |
| `distance_meters` | integer | `>= 0` and below configured sanity ceiling |
| `generated_at` | timestamptz | server generated |
| `provider` | text | normalized routing provider identifier, not a secret |

Invariants:

- Upsert only through the authenticated Edge Function/service role after
  participant validation.
- Read only by the appointment client/provider while status is `ACCEPTED` or
  `IN_PROGRESS`.
- New snapshot must not have an older location revision.
- At most one row per appointment; updates overwrite the row.
- Delete on `COMPLETED`, `CANCELLED` or other terminal transition.
- No RLS policy grants direct client insert/update/delete.

## Derived projections (not stored)

### `NearbyPitTecMarker`

| Field | Type | Notes |
|---|---|---|
| `marker_id` | string | opaque and scoped to response/time bucket |
| `latitude` | double | server-approximated |
| `longitude` | double | server-approximated |
| `accuracy_radius_meters` | integer | communicates approximation to UI |

No provider identity, exact point, price or direct contact is exposed.

### `PitTecDispatchSnapshot`

Normalized RPC result consumed by both client and provider:

- search/appointment IDs and revision;
- dispatch kind and current state;
- offer expiry for the assigned provider;
- actor-appropriate actions (`CANCEL`, `ACCEPT`, `REJECT`, `ARRIVE`, `COMPLETE`);
- for the offered provider only, approximate distance and a coarse region label
  (saved client city/state when available, never street/number); when locality is
  unavailable, use a generic distance-band label instead of precise data;
- participant display data only after acceptance;
- no exact coordinates in the snapshot itself.

Coordinates continue through the participant-only location contract.

### `RouteSnapshot`

- status: `ROUTE`, `ESTIMATED_DIRECT`, `UNAVAILABLE`;
- distance in meters;
- ordered `[longitude, latitude]` pairs;
- provider location revision and generation time;
- presentation hint: solid for routed, dashed for estimate.

`ESTIMATED_DIRECT` is calculated in memory by the Android app and is not stored.

## Authorization matrix

| Resource/action | Client requester | Assigned provider | Other authenticated user |
|---|---:|---:|---:|
| approximate PitTec discovery | yes | no | no |
| exact request point before acceptance | no direct read | no | no |
| respond to pending offer | no | yes | no |
| exact participant locations after acceptance | yes | yes | no |
| generate/read route | yes | yes | no |
| mark arrival/complete | no | yes | no |
| cancel accepted appointment with reason | yes | yes | no |

## Migration and cleanup rules

1. Preflight unknown `dispatch_kind`/`location_mode` values and duplicate active
   client searches; fail with actionable diagnostics if present.
2. Add nullable fields/table and policies before constraints that depend on
   backfill.
3. Extend checks without rewriting applied migration files.
4. Create/replace RPCs with explicit `search_path`, least privileges and grants
   only to `authenticated` where needed.
5. Seed PitTec by stable slug/key with conflict validation.
6. Add indexes for active client search, provider eligibility, offer expiration
   and candidate non-repetition.
7. Terminal RPCs delete live route/location rows in their transaction.

## Retention and observability

- Do not log coordinates, route geometry, JWTs or full RPC payloads.
- Candidate/status/timestamps remain for operational audit under the project's
  existing retention policy.
- Live participant locations and route snapshots are ephemeral and removed on
  terminal transitions.
- Metrics use counts, latency buckets, radius, error code and state—not raw
  locations or user identifiers.
